## 消息流水线

一条新消息进入后依次经过：

```
1. 去重        按 rawid 挡掉 SSE 重连 / 图片重试造成的重复事件
2. 解析        reader 的 payload → 统一内部结构（talker/kind/text/images）
3. 触发判断    白名单 + 触发模式（smart / mention / prefix / all / off）
4. 限流        每聊天每分钟上限，防止刷屏
5. 上下文压缩  估算 token，超过 compressAtTokens 就把旧消息压成摘要
6. 记忆检索    按分数挑选相关旧事，拼进 system prompt
7. 模型调用    工具循环最多 4 轮；失败自动换提供商
8. 图片处理    工具产出图片 → 自动发送 → 删除暂存
9. 回复拆分    按长度/段落切成多条，节流发送
10. 记忆沉淀   异步打标签、评重要度、写库；必要时压缩记忆
```

第 10 步是异步的，不阻塞回复——所以用户感知的响应速度只取决于第 7 步。

## 关键取舍

### 为什么零依赖

- 部署只要 `git clone` + `node`，不用 `npm install`，也不会有供应链风险
- 代价：没有现成的 Web 框架、解析库，全部手写（HTTP 路由、SSE、HTML 解析、调度）
- 结果：整个后端 8 个 `.mjs` 文件，控制台一个 HTML 文件，全都能直接读懂、直接改

### 为什么不用向量数据库做记忆检索

记忆规模是"每个聊天几十到几百条"，用**中文字符二元组 + 多维打分**足够，
而且：启动零成本、可以直接在文件里看到每条记忆、改参数即刻生效。
真需要语义检索时可以再加一层 embedding，接口已经留好（`searchMemories`）。

### 为什么记忆要"遗忘"

只增不减的记忆库会越来越吵：检索被琐事淹没、提示词被无关内容撑爆、模型开始胡联系。
遗忘曲线本质是**自动降噪**——把"重要"这个信号交给模型打分，把"时间"这个信号交给衰减公式，
两者相乘就得到一个不需要人工维护的记忆优先级。

### 为什么工具轮次用完要"强制作答"

带工具的小模型很容易陷入"再查一下"的循环。轮次用尽后关掉工具、强制它基于已收集的信息作答，
再不行就用工具结果兜底——宁可给出一份带链接的原始结果，也不让用户收到空消息。

## 并发与状态

- 每个聊天串行处理（`processing` Set），避免同一会话回复乱序
- 不同聊天之间并发，互不阻塞
- 配置、上下文、记忆全部落盘（原子写：临时文件 + rename）
- SSE 长连接带 90 秒空闲判定与指数退避重连

## 数据落地

| 路径 | 内容 | 是否可删 |
|---|---|---|
| `data/config.json` | 全部配置（含 API Key） | 删了会重新生成默认配置 |
| `data/contexts/<talker>.json` | 每聊天的对话上下文 + 摘要 | 可删（等于清空记忆上下文） |
| `data/memory/scopes/<talker>.json` | 会话记忆 + 成员记忆 + 画像 | 可删 |
| `data/memory/archived/` | 已遗忘的记忆 | 可删 |
| `data/media/pending-send/` | 待发送的图片 | 超过 24 小时自动清理 |
| `data/plugin-data/<id>/` | 插件私有数据 | 视插件而定 |
| `data/backups/` | 改动第三方配置前的备份 | 可删 |
